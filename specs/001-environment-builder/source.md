## 1. Видение продукта

Environment Builder — WPF-приложение для создания и управления изолированными контейнерными окружениями на локальном компьютере. 
Пользователь выбирает собственные приложения и инфраструктурные компоненты, настраивает их и сохраняет описание окружения.
Приложение генерирует Compose и управляет соответствующими контейнерами и данными.


Рабочее название продукта — Environment Builder;


- UI Kit: WPF UI (lepoco)
- Иконки: Lucide Icons через MahApps.Metro.IconPacks


## 2. Главные сущности

Основная сущность приложения - IsolatedEnvironment (рус. "Окружение"). Это спецификация одного изолированного окружения: идентичность, сервисы, зависимости, параметры, порты, данные.

EnvironmentComponent - Контейнеризуемое приложение или инфраструктурный компонент.

EnvironmentComponent подразделяются на 2 вида.
infrastructure (Инфраструктурные) - это сервисы вроде Postgres, RabbitMq, Kafka и так далее.
target (Целевые) - сервисы, ради которых изолированное окружение и собирается, представляют основную рабочую нагрузку. В отличие от инфраструктурных - будут иметь более кастомизированную настройку, а так же могут собираться из исходников в локальном репозитории.

SeedPack - пакет данных, который может использоваться для начального наполнения данными целевых EnvironmentComponent.
Это некий набор бизнес сущностей (пользователи, мероприятия, и т.д, зависит от бизнес-контекста целевого EnvironmentComponent)
Наборы могут отличаться тематикой (например можно добавить данные в стиле LOTR, Harry Potter, SW, либо просто Generic-office данные)
Наборы могут отличаться количеством данных. (Набор для тестирования бизнес-сценариев, набор для нагрузочного тестирования и т.д.)
Наборы могут иметь версии.
Для первой версии приложения должна быть возможность импорта Набора. Создаваться набор будет вне приложения.

На основе IsolatedEnvironment собирается compose файл для последующего запуска.

Целевые сервисы могут иметь зависимости: от других целевых сервисов, или от инфраструктурных сервисов.

При старте целевого сервиса должен быть механизм начальной инициализации (вызовы api это сервиса в определенном порядке, с определенными данными), последовательность вызова api должна задаваться как json (?) файл. Формат нужно продумать.


Другие сущности требуется выделять по мере необходимости.

## 3. Основные сценарии пользователя

1. Открыть «Окружения», увидеть сохранённые IsolatedEnvironment и их фактическое состояние.
2. Нажать «Создать», выбрать сервисы и инфраструктуру, задать параметры, проверить конфигурацию/Compose и сохранить.
3. Запустить сохранённое окружение, отслеживать ход операции и перейти в Inspect.
4. Просмотреть состав, health, ресурсы, логи, порты и адреса сервисов.
5. Остановить окружение и позднее запустить с сохранёнными данными.
6. Изменить остановленное окружение и сохранить новую ревизию.
7. Очистить все persisted-данные выбранного окружения.
8. Выполнить refresh данных выбранного окружения.
9. Удалить окружение и принадлежащие ему runtime-ресурсы.
10. Задать общие defaults и источники образов/сборки.
11. Загрузить набор данных, посмотреть содержимое и выбрать его для окружения.


## 4. Границы продукта

### Входит в основную версию

- WPF shell, навигация, список окружений, создание/редактирование, Inspect (просмотр запущенного окружения), настройки и диагностика.
- Версионируемый формат хранения IsolatedEnvironment; валидация, локальное хранение и генерация Compose.
- Целевые сервисы, настраиваемые без внесения их имён в код WPF-приложения.
- Выбор образа контейнеров целевых сервисо или сборка из выбранной папки. Для инфраструктурных - только образ, или ссылка на репозиторий с образом.
- Параметры, зависимости, ports, volumes, environment variables и безопасные ссылки на секреты.
- Запуск/остановка и наблюдение Docker; изоляция нескольких окружений.
- Полный жизненный цикл данных: сохранение при Stop/Start, явная очистка, refresh по описанному способу.
- Логи, health, доступные метрики и диагностика.
- Библиотека и preview пакетов данных; применение через поддерживаемые универсальные способы.
- Импорт/экспорт конфигурации и обработка ошибок/прерванных операций.


## 5. Функциональные требования

| ID | Требование |
| --- | --- |
| FR-01 | Главная сущность в документах и новой модели называется IsolatedEnvironment. В интерфейсе допустим короткий термин «окружение». |
| FR-02 | IsolatedEnvironment сохраняется в специальном формате (предложить) и содержит целевые сервисы и инфраструктурные сервисы. |
| FR-03 | Из IsolatedEnvironment генерируется Compose для полного выбранного состава; предварительный просмотр соответствует будущему запуску. |
| FR-04 | При открытии приложения пользователь попадает на список «Окружения», включая пустое состояние. |
| FR-05 | Список показывает имя/описание, состав сервисов и инфраструктуры, состояние, доступные метрики и команды. Предусмотрены поиск, фильтры и раскрытие компонентов. |
| FR-06 | «Создать» открывает вложенный экран создания IsolatedEnvironment. Сохранение создаёт спецификацию без запуска контейнеров. |
| FR-07 | В редакторе задаются имя, описание, состав, источники образов/сборки, параметры, зависимости, порты, хранилища и выбранные данные. |
| FR-08 | ID неизменяем. Редактирование разрешено после подтверждённой остановки. Несохранённые изменения защищены модальным подтверждением при уходе. |
| FR-09 | сохранение изменённого существующего окружения сопровождается предупреждением и очисткой прежних runtime-данных, затем создаётся новая ревизия с тем же ID. Это правило относится и к изменению только имени. |
| FR-10 | «Запустить» проверяет входы, подготавливает образы/Compose и запускает нужный состав. Ошибка одного компонента видна отдельно. |
| FR-11 | «Остановить» завершает работу контейнеров с сохранением persisted-данных. Повторный Start не переигрывает уже успешно применённые данные. |
| FR-12 | «Очистить данные» удаляет все принадлежащие окружению persisted-данные в явно перечисленном плане; спецификация сохраняется. |
| FR-13 | «Refresh данных» поддерживается как самостоятельная операция. Предлагаемая семантика — восстановление выбранного baseline, с предварительным предупреждением о потере текущих данных. |
| FR-14 | «Удалить» удаляет IsolatedEnvironment и принадлежащие ему runtime-ресурсы/данные после подтверждения. Частичная ошибка не скрывает остатки. |
| FR-15 | Inspect показывает фактический состав, Docker status/health, ports, endpoints, логи и доступные метрики выбранного окружения. |
| FR-16 | Действия над отдельным сервисом отображаются только с понятными назначением и доступностью. Наличие иконки не означает, что действие технически поддержано. |
| FR-17 | Настройки позволяют выбрать готовый image или Build из папки для каждого компонента, задать общие defaults и специфические параметры. |
| FR-18 | Изменение глобальных defaults само по себе не меняет сохранённые окружения. |
| FR-19 | Пользователь может описать собственный сервис через универсальные параметры; Удобный способ добавления требует проектирования. |
| FR-20 | Зависимости отображаются явно; автоматически добавленный компонент имеет причину включения. Цикл или отсутствующая обязательная зависимость блокируют некорректный запуск. |
| FR-21 | «Тестовые данные» предоставляет загрузку, удаление, выбор пакета и текстовый preview. Импорт пакета сам по себе не изменяет окружения. |
| FR-22 | Preview пакета работает без контейнеров. Доменные секции вроде «встречи» появляются по содержимому/возможностям пакета, а не обязательны для всех. |
| FR-23 | Импорт/экспорт переносит спецификацию без секретов и runtime-данных. Отсутствующие локальные пути/образы/пакеты перечисляются как проблемы, а не подменяются рабочими настройками. |
| FR-24 | Диагностика показывает доступность Docker/Compose, пути, конфигурацию, images/build inputs, конфликты ports и проблемы собственных ресурсов. Исправления выполняются отдельными действиями. |
| FR-25 | Долгие операции имеют прогресс, результат и ошибку; интерфейс остаётся отзывчивым. Уход со страницы не теряет выполняемую операцию. |
| FR-26 | После перезапуска приложения состояние сверяется с Docker. Недоступность Docker означает неизвестное/устаревшее наблюдение, а не «Остановлено». |
| FR-27 | Несколько окружений изолированы по управляемым ресурсам; очистка/refresh/удаление одного не затрагивают другое или чужие контейнеры. |
| FR-28 | Приложение показывает только измеренные метрики и вычисленные счётчики. Отсутствующее значение отличается от нуля. |

## 6. Экраны и навигация

Основные разделы: «Окружения», «Тестовые данные», «Настройки», «Диагностика».

Внутри «Окружений»: список -> создание; список -> редактирование; список -> Inspect. Compose preview открывается в контексте текущего окружения/редактора.

После создания приложение возвращает пользователя в список и показывает созданное окружение. После сохранения, отмены и возврата поиск/фильтры/позиция по возможности сохраняются.

## 7. Данные и безопасность операций

Три разные команды: обновление наблюдения перечитывает состояние контейнеров; очистка удаляет persisted-данные; refresh меняет сами данные по выбранному baseline/provider. В интерфейсе эти команды должны иметь разные подписи и подтверждения.

Первая версия рекомендуется для локального Docker и Linux-контейнеров; окончательная support matrix открыта. Приложение создаёт отдельный Compose project и ресурсы окружения. Оно не выполняет общий Docker prune и не принимает совпадение имени за доказательство владения.

Экспорт, preview, логи и сообщения об ошибках не содержат секреты. Указание папки исходников, импорт JSON или пакета не запускают содержащийся там код.

## 8. Ожидаемое качество

- Оформление следует пяти макетам: светлый фон, белые панели, синие действия, плотные таблицы, иконки, понятные состояния.
- Макеты приложены как референс их не требуется повторять 1 в 1.
- Длинные имена, пустые/большие списки, ошибки, неизвестное состояние и отсутствие Docker имеют полноценное отображение.
- Клавиатурная навигация, подписи иконок/tooltip, resize и DPI проверяются при реализации UI.
- Логи/метрики ограничены по памяти; подписки переключаются вместе с выбранным окружением.
- Приёмка основного продукта выполняется на независимом демонстрационном наборе контейнеров, (нужно создать 3 демо dotnet сервиса, взаимодействующих через rabbitMq например).
